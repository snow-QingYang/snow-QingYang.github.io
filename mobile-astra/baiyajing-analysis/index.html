怎么理解这些结果

33 个修复成功，不是 33 个纯解析接管

20 个只在程序层使用 vla/pick，仍包含 Planner 选择子任务文本、目标位置和停止条件。另 13 个加入 carry / put_down / release / goto 等显式步骤。

pick 也由 VLA 抓取；vla/pick 内部还会自动导航、调整手臂、处理持物和撤离。不能直接沿用官方 RPent 的“非 VLA 工具数”作为分类依据。

剩余子任务可以比整任务更有效

例如 LoadDishwasher seed 1：首次 VLA 已放好餐具但没关门。Planner 改用 Close the dishwasher door.，13 个 chunks 后完成任务。Baiyajing 会实际执行这些子任务 prompt。

33 个成功都执行过与原始完整任务不同的 prompt，且均有实际 Planner 程序步骤。日志中的自动 fallback 没有产生额外成功。

成功判定和步骤返回要分开看

ok=true 只表示某个程序子步骤通过检查，done 可能只完成一个子目标。完整任务以最终环境 success 为准；env_success 是 attempt 的明确成功信号。

修复成功的最后一个程序 op 为：vla 28 个、put_down 2 个、carry 2 个、release 1 个。vla 内部可能自动撤离，因此这不是纯神经策略 / 解析动作的因果划分。

初始整任务 VLA 在哪里停止

这是首次 attempt 的状态：budget 指该次 VLA 的 chunk 预算；和最终 57 个整局时间预算失败不是同一个统计。

实际执行了哪些程序方法

统计实际进入执行器的 1,414 个程序步骤，包含未通过子目标检查的步骤；未执行的计划内容不计数。自动 fallback 共 32 步，全部来自失败 episode。

成功路径的耗时中位数

各组任务与难度不同。耗时包含执行器、Planner、VLA 和启动 / 收尾开销，不是模型推理速度对比。

计数层级

1,047 次 Planner 调用 → 1,414 个已执行程序步骤 → 1,928 次实际 VLA attempts。一个程序可有多个步骤，一个步骤可重试多次，一个 attempt 又包含多个 chunks；每 chunk 是 8 个控制步。

统计口径、实现差异与数据来源

本报告的分类规则

  1. 初始整任务 VLA：首次固定的 vla 步骤成功，只有一个程序步骤，Planner 调用为 0。28 个案例均满足这些条件。执行器初始化和环境反馈仍在运行，不是完全无 harness 的独立 VLA 基线。
  2. Planner 修复：首次 VLA 未完成，随后执行 Planner 输出的程序，最终环境成功。按执行过的 op 分成仅 vla/pick 与包含显式非 VLA op 两类；这是观察性路径分类，不证明每一步都必不可少。
  3. 计划与实际执行分开展示：排队但未执行的步骤保留在计划 JSON；执行器生成的 fallback 单独标注。每个步骤保留参数、attempt 返回和前后判据。
  4. 最终结果使用环境 check_success() 写入的 result.json.success。逐例核对程序步数、Planner 次数、VLA chunks、末步判据与 result；160 个 episode 均一致。
  5. object_fell 事件本身不等于整局失败：这批有 2 个出现过物体丢失事件的成功案例。终止标签 object_on_floor 则需物体已丢失且 Planner 返回不可恢复。
