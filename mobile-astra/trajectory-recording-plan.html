旧实验记录保留计划、高层步骤、检查摘要、截图和 VLA 片段；缺少逐步动作与完整状态。将新记录机制用于后续实验。旧数据不具备补成原始完整轨迹的条件。

02 · 保存什么：三条记录使用同一套编号

环境端生成权威的 episode_id / segment_id / state_id。方法调用使用 call_id / parent_call_id，通过调用上下文与环境端关联，不依赖两个进程各自估算帧号。

state[0]reset 后的实际现场
→
action[0]实际送入 env.step
→
state[1]执行后的现场
→ …

每个正常结束的 segment：N 个动作 = N 次 env.step；N+1 个状态。

“逐步”按环境控制步记录（频率写入 manifest），不是 MuJoCo 求解器内部的每个物理子步。再次 reset 会开始新 segment，视频和索引必须明确标记边界。

记录必须保存的字段用途与约束
场景与来源
manifest / model / ep_meta		任务、seed、实际场景 XML、episode metadata、相机配置、控制频率、控制器配置、代码版本、MuJoCo/robosuite/RoboCasa 版本、模型标识、资产引用与哈希、schema 版本。恢复实际生成的场景，不能只靠 seed 重新随机初始化。资产需可定位、可校验，导出时支持打包或连接可访问的共享资产目录。
每步实际动作
action[i]		动作向量、dtype/shape、控制步编号、执行前后 state_id、仿真时间、墙钟时间、所属 call_id、原始 reward/done/info。保存经过裁剪和转换后真正送入 env.step 的动作。VLA 输出 chunk 单独保存并关联，明确哪些预测步实际执行。
MuJoCo 状态
state[i]		按安装版本的 mjSTATE_INTEGRATION 保存积分状态，包括 qpos/qvel、act、ctrl、warmstart、mocap、外力等受支持字段；保留精度、状态 mask 和维度。使用 mj_getState / mj_setState。当前 robosuite 的 sim.get_state() 只含时间、qpos、qvel，不能单独充当完整状态快照。
任务及视觉状态
task_state / visual_state		RoboCasa 在 Python 层维护的任务与 fixture 状态；如 toaster 的 turned_on、加热计数、冷却计数；运行中变化的材质、颜色、灯光等 model 字段。建立显式状态适配器和任务覆盖表。未知或无法恢复的字段必须记录为覆盖缺口，不能仅凭文件存在就标记“可完整回放”。
每次方法调用
methods.jsonl		call_id、parent_call_id、method、调用层级、完整参数、返回值/异常、开始/结束时间、开始/结束 state_id、关联观测引用。覆盖 Planner、程序执行、Robot、导航、env 与 VLA RPC。实际调用和计划中尚未执行的步骤分别展示；环境 step 逐项保留。
实际观测
observations/		感知调用真正返回的图像和数组，保留相机名称、尺寸、朝向、dtype/shape、内容哈希；大数组以文件引用保存。相同内容去重、无损保存。右侧显示当时模型/执行器真正看到的观测；补录用的相机渲染不计为 agent 的 perception 调用。
拟定的 episode 目录与分块字段
episode/
  manifest.json             # schema、配置、资产引用、完整性与最后提交步
  model.xml                 # 实际场景
  ep_meta.json               # episode 配置与物体 / fixture / 相机信息
  trajectory/
    initial_state.npz        # state[0]，reset 后立即保存
    chunk_00000.npz          # actions、post_states、时间、call_id
    chunk_00001.npz
    task_state.jsonl         # 与 state_id 关联的任务 / 视觉状态或增量
  methods.jsonl              # 方法开始 / 结束，包含嵌套父调用
  observations/              # 无损图像、数值数组，按内容去重
  result.json                # 原实验结果与轨迹状态分开记录
  episode.mp4                # 可选；离线生成的派生产物
  replay_index.json          # frame ↔ state_id ↔ call_id
  verification.json          # 实际检查结果与未覆盖项

分块保存时只存一次初始状态，之后每个 action 对应一个 post_state，避免相邻块重复计算状态数。数组 shape/dtype、分块范围和校验和均写入 manifest；JSON 不将浮点状态截断到展示精度。

落盘与中断

分块压缩，临时文件写完后原子提交；记录 last_committed_step。正常退出、超时、SIGTERM 执行 flush。SIGKILL/断电只承诺恢复已提交前缀，缺失尾段明确标注。

写盘队列有容量限制，满载时阻塞或明确报错，不丢帧；磁盘不足不能静默关闭记录。

对实验的影响

采集保持原来的 reset 和动作序列，只读状态、写入记录。复用实际检查的返回值，避免为了日志额外调用可能改变任务计数的检查器。

记录会产生开销；单独统计 I/O 与快照耗时，保留原墙钟预算口径，并在实验配置中标明。

04 · 离线视频与右侧方法如何对应

  1. 加载实际场景

    校验 manifest、版本、XML 和资产；使用记录的 ep_meta 恢复相机与对象配置。资源缺失时明确指出缺什么。

  2. 直接恢复每个已保存状态

    依次恢复 MuJoCo、任务和视觉状态，刷新派生几何后渲染画面。画面位置来自已保存状态；渲染过程中无需重新计算 VLA 动作，也不推进任务计时器。

  3. 生成连续视频与索引

    完整控制频率回放时，一个 state 对应一个视频帧，N 个控制步得到 N+1 帧。选择抽帧导出时保存显式 frame → state_id 映射，不能再直接假设帧号等于步号。

  4. 网页关联真实方法

    点击任何调用跳到它开始时的状态；展开查看参数、结果、异常和实际观测。Planner 等待期间仿真不前进，多次感知可以对应同一帧，墙钟耗时单独展示。

示例调用关系（结构示意，不是一次真实实验结果）

Planner.replan → 返回剩余程序
Episode.run_step(op="carry")
Robot.goto → BaseNavigator.go
env.robot_pose / env.step / …
Robot.held_object → env.check

Planner 产出程序，执行器负责具体控制与检查。网页按实际调用层级标注，不把自动感知包装成模型亲自调用的方法。

CPU 的职责

逐状态离线恢复、软件渲染和视频编码可以单独运行，不加载 RLDX。CPU 渲染耗时在集成测试中测量，结果写入验证报告。

交付边界

本阶段保证可验证的逐帧画面恢复与调用审计。从任意中间状态继续控制机器人，还涉及控制器和策略内部状态，需另行验证，不能由“视频能回放”推导出来。

05 · 按这个顺序实施

阶段工作进入下一阶段的条件
P0 · 数据约定固定 schema、状态编号、RPC 调用上下文、分块提交规则和任务状态覆盖清单。明确字段、所有权和完整性规则；标出未覆盖的 fixture 状态。
P1 · 轨迹保存在环境层保存 reset 快照、每个实际动作、状态、场景与资产信息。真实环境动作与状态对齐；没有漏掉导航、恢复或放下阶段。
P2 · 独立恢复实现离线恢复和 CPU 渲染，核对位置、关节、相机及动态 fixture/视觉状态。关闭 VLA 后，独立进程仍能从首帧、中间任意帧和末帧恢复。
P3 · 完整方法日志接入 Planner、程序入口、控制和感知调用，保存实际观测，打通 call_id ↔ state_id。调用关系、输入输出、错误和图像引用完整；跨进程位置一致。
P4 · 正式入口与稳定性接入单次/批量入口，完成中断、资源失败、记录开销和覆盖范围验证。记录问题不会伪装成正常完整轨迹；测量时间预算影响。
P5 · 网页交付选取有 Planner 介入、实际成功和实际失败各一例，导出视频与完整方法时间线。下方适用验收项通过并附证据，再部署到 mobile-astra 的独立工作目录。

先证明“保存后确实可以恢复”，再用于下一批正式实验。旧的 160 次实验结果保留原统计；补录案例标明新的运行日期、配置与实际结果。

06 · 实现后如何验收

以下 12 项当前全部待验证

每项通过时都要提供可打开的产物或验证输出。网页展示正确、文件存在、控制台没有报错，都不能单独替代轨迹完整性验证。

编号 / 项目检查方法通过标准 / 证据
A01 · 全控制路径真实环境覆盖 VLA、导航、抓取准备、carry、put_down、撤离与恢复动作。服务端 step 计数与归档动作数一致；每个实际动作都能定位来源调用。
A02 · 状态与动作对齐检查初始状态、所有分块、时间与编号，包括分块交界处。每个完整 segment 满足 N 动作 / N+1 状态；无重复、缺号或错位。
A03 · 独立随机访问新进程恢复首帧、随机中间帧与末帧；不先播放前面的动作。恢复后的状态数值与存档一致；指定对象/关节/相机与原场景一致，附对照图。
A04 · 任务与视觉状态检查 toaster 开关及计数、门、动态灯光/颜色等；列出 32 个任务的适配覆盖。同一 state_id 的状态和画面正确；未支持内容显式列出，不能标记全覆盖。
A05 · 无模型 CPU 回放关闭 VLA 服务，在没有 CUDA 设备的渲染进程中生成完整视频。无模型加载和推理请求；生成可播放 MP4，并报告实际耗时与峰值内存。
A06 · perception 证据随机抽取 render_camera、check、grasp_contact、robot_pose 等调用。输入、返回值、时间、状态编号和观测文件齐全；图片朝向、维度与原返回值一致。
A07 · 嵌套与异常检查 Planner → 程序 → Robot/导航 → RPC；制造一次可控调用错误。父子编号及边界正确；错误调用有开始和异常结束记录，未执行计划不计为调用。
A08 · 重置与退出覆盖再次 reset、正常结束、超时、SIGTERM，以及独立的 SIGKILL 测试。reset 分段明确；可收尾退出保存尾段；强杀时能读取已提交前缀并标记 incomplete。
A09 · 写盘失败与损坏模拟磁盘空间不足、写入失败、缺失观测和损坏分块。检查器明确失败并定位文件/首个错误编号；不静默丢记录，不误判为完整。
A10 · 采集开销固定动作序列，比较启用/关闭记录的执行轨迹、耗时与体积。采集不增加 reset/控制步；轨迹符合预定数值容差；耗时和空间实测写入报告，保留墙钟预算口径。
A11 · 网页同步从视频和方法两侧分别跳转，包含同帧多次感知、Planner 等待及失败终止。视频、state_id、call_id 对齐；完整控制频率导出为 N+1 帧；参数、返回值、图像可查看。
A12 · 案例与部署有 Planner 介入的实际成功、实际失败案例各一例；核对来源和公开路径。结果来自环境实际判定；补录与原统计分开；仅更新 mobile-astra 工作页，个人站点页面无改动。
